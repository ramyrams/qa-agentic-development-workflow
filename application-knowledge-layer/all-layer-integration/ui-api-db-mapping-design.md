# UI → API → Database Mapping — Design

## Goal

Extend the page-capture pipeline so every UI action links to the API call(s) it triggers, and every API call links to the database table(s) it touches — producing a full-stack trace: **element → API endpoint → DB table**. This completes the [[application-knowledge-layer]] vision (business rules, workflows, pages, elements, DB schema, API contracts all connected).

## Constraint that shapes this design

Your sources are mixed quality, not uniform:
- Backend source: reachable for **some** services, not all.
- OpenAPI spec: exists but **outdated/incomplete**.
- DB schema: available as **DDL export**, not live introspection.

This means the design can't treat every link as equally trustworthy. The core design decision is: **tag every API and trace record with its source and confidence**, and never silently upgrade an inferred link into a confirmed one. Getting this wrong is worse than having gaps — a confidently-wrong trace will produce confidently-wrong test steps downstream.

---

## 1. New artifact types

| Artifact | Contains | File | Captured from |
|---|---|---|---|
| **API contract record** | Method, path, auth, request/response shape, backing handler, tables touched | `api/<endpoint-id>.yaml` | OpenAPI import + observed traffic + code trace (reconciled) |
| **DB table record** | Columns, types, keys, FKs, relationships | `db/<table-id>.yaml` | Parsed from DDL |
| **Trace record** | element → api endpoint → table(s), with rolled-up confidence | `traces/<trace-id>.yaml` | Auto-generated by linking the two above |

Page records gain one new field per element that triggers a backend call:
```yaml
elements:
  - name: continue-button
    role: button
    selector: "role=button[name='Continue to Payment']"
    strategy: role
    api_calls:
      - endpoint_id: post-checkout-shipping
        triggered_on: "click, valid form state"
```
The request/response detail itself lives once in the API contract record — the page record only references the endpoint id, same dedup principle used for shared components.

## 2. Schema examples

**API contract record** (note the `source`/`confidence` fields — this is the part that matters given your mixed access):
```yaml
id: post-checkout-shipping
method: POST
path: /api/checkout/shipping
auth_required: true
source: reconciled              # openapi-spec | observed | code-trace | reconciled
confidence: high                # low | medium | high
spec_status: "confirmed via observed traffic; not in current OpenAPI spec"
request_schema:
  address_line1: string
  zip: string
response_schema:
  status: string
  order_id: string
backing_handler: "services/checkout/shippingController.ts#submitShipping"   # only if code-traced
tables_touched:
  - orders
  - shipping_addresses
tables_touched_confidence: code-traced   # code-traced | inferred | unknown
```

**DB table record** (mechanically parsed from DDL — no agent judgment needed):
```yaml
id: orders
source: ddl-export
columns:
  - name: id
    type: uuid
    primary_key: true
  - name: user_id
    type: uuid
    foreign_key: users.id
  - name: status
    type: varchar
relationships:
  - table: shipping_addresses
    type: one-to-many
```

**Trace record** (the payoff artifact — this is what answers "what does this button ultimately touch in the database"):
```yaml
id: checkout-continue-button-trace
page_id: checkout-shipping
element: continue-button
api_endpoint: post-checkout-shipping
tables_touched: [orders, shipping_addresses]
overall_confidence: medium   # weakest link in the chain — here, capped by tables_touched_confidence
```

## 3. Capture workflow per layer

### 3a. DB layer — mechanical, do first, independent of everything else
Parse the DDL export into `db/<table>.yaml` records with a script, not an agent judgment call — column names, types, keys, and FKs are unambiguous in DDL. This has no dependency on the UI walkthrough and can run any time the DDL is refreshed.

### 3b. API layer — reconcile three sources, don't trust any one alone
1. **Import the OpenAPI spec** as baseline records, `source: openapi-spec`. Mark every field confidence `low` — it's known to be stale.
2. **Extend `capture-page`** with a new step: while performing each action during a page capture session, record the network requests fired (method, path, request/response body) using the browser's network layer. This is ground truth for *what the UI actually calls right now*, independent of whether the spec agrees.
3. **Run a reconciliation step** after each capture session: match observed calls to spec records by method+path.
   - Observed but not in spec → new record, `source: observed`, flag as "spec gap — consider filing a spec update."
   - In spec but never observed → leave as-is, flag as "unconfirmed — may be dead or just not yet walked."
   - Matches on both → merge, `source: reconciled`, request/response shape upgraded to whichever is more complete.
4. **Where backend source is reachable**: run a code-trace step — Copilot follows the route handler to its service/repository layer and extracts the table(s) it reads/writes. This is the *only* step that can populate `tables_touched` with confidence `code-traced`. Upgrade the record's overall `confidence` to `high`.
5. **Where backend source is not reachable**: `tables_touched` stays empty or is filled by manual annotation from someone who knows that service, explicitly tagged `tables_touched_confidence: inferred` or `unknown`. Never let an agent guess table names from the response shape and record it as if it were code-traced.

### 3c. Linking — automated, runs after 3a and 3b
A small script joins page-record `api_calls` → API contract records (by `endpoint_id`) → DB table records (by `tables_touched`), and writes the trace record with `overall_confidence` set to the weakest confidence level anywhere in the chain. This is deterministic — no agent judgment needed once the two source layers exist.

---

## 4. Why observed traffic outranks the spec

Given the spec is outdated, treat it as a *starting point*, not ground truth. The reconciliation step in 3b is the part that keeps the knowledge base honest: an endpoint the UI actually calls but the spec doesn't mention is a real gap worth surfacing (possibly worth a ticket to fix the spec itself), not something to silently paper over by trusting the spec.

## 5. Sequencing

| Phase | Deliverable | Depends on |
|---|---|---|
| 0 | DDL parser script → db/*.yaml records for all tables | — (independent, run anytime) |
| 1 | OpenAPI spec importer → baseline api/*.yaml records, confidence=low | — (independent) |
| 2 | capture-page extended to log network calls during actions | Existing capture-page skill (already built) |
| 3 | reconcile-api-contract skill — diff observed vs. spec | Phase 1, 2 |
| 4 | code-trace skill for reachable backend services — populates tables_touched, confidence=code-traced | Phase 3, backend source access per-service |
| 5 | Manual annotation pass for unreachable services — tables_touched=inferred/unknown, explicitly flagged | Phase 3, where Phase 4 isn't possible |
| 6 | Linking script — generates trace records from api-calls + api contracts + db tables | Phase 0, 3, (4 or 5) |
| 7 | Extend `audit-capture-quality` to also flag traces with confidence below a threshold, so low-confidence links surface for review rather than sitting silently | Phase 6 |

Phases 0 and 1 can start immediately, in parallel with anything else — they don't depend on the UI walkthrough at all.

---

## 6. Key trade-off

Chasing `tables_touched` confidence up to `code-traced` for every endpoint is expensive if it means manually reviewing services you don't have source access to. For those, accept `inferred`/`unknown` as a permanent state for now rather than blocking the rest of the pipeline on backend access you don't control — and let the confidence field do its job: a test-step generator or Q&A skill consuming this later can decide whether to trust or flag a low-confidence trace, rather than the pipeline pretending certainty it doesn't have.

## 7. Open decisions

- Who requests backend source access for the remaining unreachable services, and whether that's worth pursuing given the manual-annotation fallback.
- Whether to file spec-gap tickets automatically from the reconciliation step, or just log them for now.
- DDL refresh cadence — one-time import vs. periodic re-parse as schema evolves.
