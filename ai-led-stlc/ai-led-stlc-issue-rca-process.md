# AI-Led STLC — Issue Identification, RCA & Resolution Process
### What Happens When an Agent or Skill's Output Is Wrong or Inconsistent

This is the process that runs whenever something in Sections 5-6 of the Governance Model actually fires — a rejected draft, a calibration gap, a ledger anomaly, a metrics threshold breach. It closes the loop those mechanisms open: find the issue, document it consistently, find the real cause (not just the symptom), fix it, verify the fix, and make sure it can't silently recur.

---

## 1. Where Issues Come From

Don't wait for someone to notice something's wrong — issues should surface through defined channels, not luck:

| Source | What It Catches |
|---|---|
| Human review rejection/edit (any activity's approval gate) | Individual bad outputs, caught at the point of use |
| Reviewer Calibration Audit (Governance Model §6) | Reviewer drift, ambiguous acceptance bars |
| Failure/case-quality ledger anomaly (a category's confidence or acceptance rate degrading) | Systemic drift over time, not visible in any single output |
| Eval suite failure or determinism-score drop (Eval & Determinism Plan §B.5) | Regressions introduced by a skill/instructions/model update |
| Metrics threshold breach (Governance Model §5, leadership briefing §7) | Activity-level quality decline |
| Direct report from a tester/engineer using the output | Anything the automated channels miss |

Every one of these should route to the same intake process below — a rejection logged only in a reviewer's head, or a pattern noticed but not written down, is the most common way this whole system quietly stops working.

---

## 2. Step 1 — Identification & Intake

1. Whoever notices the issue (or the automated trigger) logs it immediately using the Issue Record template (Section 6) — even a minimal first pass is fine, it gets filled in during RCA
2. Assign initial severity using the existing Escalation Matrix (Governance Model §4): Sev1/Sev2/Sev3 — this determines urgency, not yet root cause
3. Log the issue against the specific primitive(s) involved (agent/skill/instructions/prompt name and version, from that primitive's frontmatter) — never log "the AI got it wrong" without naming the exact primitive and version, or RCA has nothing concrete to start from
4. For Sev1: Program Sponsor and AI Governance Team notified immediately per the existing escalation matrix, in parallel with — not instead of — starting the intake record

---

## 3. Step 2 — Documentation (Issue Record Template)

Every issue gets the same structured record, regardless of severity — consistency here is what makes patterns visible later:

```yaml
issue_id: <auto-generated>
date_identified: 
source: [human_review_rejection | calibration_audit | ledger_anomaly | eval_failure | metrics_breach | direct_report]
primitive_affected: <agent/skill/instructions/prompt name>
primitive_version: <version at time of issue>
stlc_activity: <from Governance Model §2>
severity: [Sev1 | Sev2 | Sev3]
symptom: >
  What was observed — the actual wrong/inconsistent output, quoted or
  referenced exactly, not paraphrased. Include the input that produced it.
expected_output: >
  What should have happened instead.
reproducibility: [always | intermittent | one-time]
  # If intermittent: this is a strong early signal the issue is a determinism
  # problem (Eval & Determinism Plan Part B), not a logic bug — route accordingly
root_cause_category: <filled in during Step 3, not at intake>
root_cause_detail: <filled in during Step 3>
fix_applied: <filled in during Step 4>
verification_method: <filled in during Step 5>
regression_case_added: [yes/no] <filled in during Step 6>
status: [open | root-cause-identified | fix-in-progress | verifying | closed]
```

Store these in a running issue log per primitive (or a shared queryable log across all primitives, once volume justifies it) — this log is what makes pattern detection possible later, the same way the failure ledger does for test failures.

---

## 4. Step 3 — Root Cause Analysis

Not every wrong output has the same kind of cause. Triage into one of these categories first — the category determines which fix type applies, so getting this step right matters more than any other:

| Category | What It Looks Like | How to Confirm |
|---|---|---|
| **A. Input/context issue** | The skill/agent got incomplete, malformed, or unexpectedly-shaped input | Check the actual input against the skill's input schema (technical design §0.2) — did it validate, or should it have been rejected upstream? |
| **B. Instructions issue** | The rule/taxonomy/convention the skill should have followed was ambiguous, missing, or contradicted by another instructions file | Check whether the relevant instructions file (Eval Plan §A.3) actually covers this case; run the compliance test with/without that instructions file |
| **C. Skill logic issue** | The skill's own reasoning or algorithm produced a wrong result even with correct input and correct instructions | Reproduce with the exact input in isolation; check against the skill's own eval suite — did this case exist there, and did it pass? |
| **D. Agent orchestration issue** | The right skills existed and worked correctly in isolation, but were called in the wrong order, with a bad handoff, or the human-review gate was mishandled | Compare actual trajectory against expected trajectory (Eval Plan §A.2.1) |
| **E. Determinism/model issue** | Reproducibility is intermittent on the same input | Run the N=10 repeated-trial protocol (Eval & Determinism Plan §B.4) — is this within the primitive's expected consistency tier, or a genuine regression? |
| **F. Data/ledger issue** | The skill's decision relied on ledger data (failure ledger, case-quality ledger, defect history) that was itself wrong, stale, or insufficiently normalized | Check the source ledger entry directly — this is a data-quality problem, not a model problem, and the fix belongs in the ledger pipeline, not the consuming skill |
| **G. Eval gap** | The skill/agent has been behaving this way for a while, but nothing caught it because no eval case covered this scenario | Confirm this input pattern is genuinely absent from `evals.json` — this category always co-occurs with one of A-F as the deeper cause, it's never sufficient on its own |
| **H. Human process issue** | The output was actually fine or borderline, and the "issue" is a reviewer/calibration disagreement, not a system defect | Cross-check against Governance Model §6.3 — route to reviewer coaching or acceptance-bar clarification, not a code fix |

**Method**: for categories A-F, use a simple 5-Whys pass grounded in actual artifacts at each step (the input, the instructions file, the eval history, the trajectory log, the ledger entry) — not speculation. If you can't point to a concrete artifact at each "why," you haven't found the cause yet, you've found a plausible guess.

**Note the co-occurrence rule for category G**: an eval gap is almost always paired with another category — the real question is always "why didn't eval catch this," and the answer is always one of A-F. Log both.

---

## 5. Step 4 — Solution Identification

The root cause category maps to where the fix belongs — don't fix a Category B problem by patching skill code, and don't fix a Category C problem by rewriting instructions:

| Root Cause | Fix Goes Here |
|---|---|
| A. Input/context | Tighten the input schema validation upstream; reject malformed input before the skill call rather than letting the skill guess |
| B. Instructions | Update the relevant instructions file; re-run the compliance test (Eval Plan §A.3.1) to confirm the update actually changes behavior |
| C. Skill logic | Fix the skill; add the failing case to its `evals.json` as a permanent regression test (Step 6) |
| D. Agent orchestration | Fix the agent's orchestration sequence or handoff logic; add the scenario to the agent's trajectory eval set |
| E. Determinism | Apply the relevant technique from the Determinism Plan (Part B) — schema-constrained output, temperature adjustment, or tier reclassification if the primitive was mis-tiered to begin with |
| F. Data/ledger | Fix the ledger pipeline (e.g., signature normalization logic, per technical design §0.3) — not the consuming skill, which was working correctly on bad data |
| G. Eval gap | Add the case to the relevant eval suite — always paired with fixing the underlying A-F cause, never a fix on its own |
| H. Human process | Route to Governance Model §6.3 — coaching conversation or acceptance-bar clarification, not a build task |

For any fix touching a skill, agent, or instructions file, this is also the point to check the Consolidation Opportunities note (Build Inventory) — if the same root cause could affect a shared instructions file's other consumers, fix it once at the shared level, not per-skill.

---

## 6. Step 5 — Fix Verification

A fix isn't done when it looks right — it's done when it passes the same bar the original primitive had to pass:

1. Re-run the full eval suite for the affected primitive, not just the failing case — confirm the fix didn't break something else (this is standard regression-test discipline, same as your existing eval-before-production policy)
2. For Category E (determinism) fixes specifically: run the full N=10 repeated-trial protocol, not a single confirmation run — a determinism fix that "looks fixed" on one run hasn't actually been verified
3. For Category D (orchestration) fixes: re-run trajectory grading against the expected trajectory, including confirming the human-review gate still fires correctly
4. Sev1 issues: verification requires sign-off from the Program Sponsor before the fix is considered closed, not just the engineer who made the change

---

## 7. Step 6 — Closure & Learning Loop

This is the step most teams skip, and it's the one that actually prevents recurrence:

1. **Add the original failing case to the primitive's permanent `evals.json`** — every resolved issue becomes a regression test forever, so this exact failure mode can never silently reappear undetected
2. **Update the relevant ledger or memory file** (per the ECC-inspired memory layer) if the issue revealed a pattern worth the agent remembering — e.g., "this signature type over-matches in duplicate-check, deprioritize it" goes into that agent's memory file, not just the issue log
3. **Update the instructions file** if Category B or if the RCA revealed the rule set needs clarifying, even if that wasn't the primary root cause
4. **Close the issue record**, with `regression_case_added: yes` — an issue closed without a regression case added is not actually closed, it's just no longer visible
5. **Pattern review**: at your existing reporting cadence (implementation plan §8), review closed issues across the period — three Category B issues in the same instructions file in one month is a signal that file needs a structural rewrite, not three independent small fixes

---

## 8. Roles

| Role | Responsibility in This Process |
|---|---|
| Whoever identifies the issue | Logs the initial Issue Record (Step 1-2) — anyone, not gated to a specific role |
| Primitive owner (the engineer/team who built the affected skill/agent) | Leads RCA (Step 3) and implements the fix (Step 4-5) |
| Program Sponsor / Steward | Sev1 sign-off; owns the monthly pattern review (Step 7.5); escalates systemic patterns to AI Governance if a data-boundary or scope issue is revealed |
| Calibration Auditor (when the source is §6 of the Governance Model) | Provides the original finding as the issue's starting documentation |

---

## 9. Quick Reference: The Loop

```
Issue observed → Logged (Issue Record) → Severity triaged (existing Sev1/2/3 matrix)
   → Root cause category identified (A-H) → Fix applied at the correct layer
   → Verified (full eval re-run + determinism check if applicable)
   → Closed with a permanent regression case added
   → Reviewed for patterns at the next reporting cycle
```

No step in this loop is optional for Sev1/Sev2 issues. For Sev3, the loop still runs, just without the urgency — an issue that's individually low-stakes but recurring is exactly what the pattern review in Step 7.5 is designed to catch before it becomes a Sev2.
