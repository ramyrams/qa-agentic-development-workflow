1

Why agent failures stay quiet

Watch: 0:52 to 2:12

In everyday life

Your phone says a package was delivered, but the porch is empty. The notification is confident and complete. To find out what went wrong, you open the tracking history and see every scan. There you find it was dropped at the wrong depot two stops earlier.

In AI agents

An agent's final answer is the "Delivered" notification. It can read as complete and polite while something went wrong upstream. The tool calls might all have "succeeded," your logs might show no errors, and the path might look sensible. The outcome can still be wrong.

Once an agent is in production, whether it is a support agent, a research assistant, an internal copilot or a tool-calling workflow, you need to keep evaluating it. You want to catch failures before they repeat. You also want to confirm that changes don't break what already worked, so users get a consistently good experience. The hard part is that the failure usually isn't visible in the response. It could be any of these:

  • Wrong context: the agent retrieved the wrong document or record.
  • Right context, wrong answer: the tools returned good data, but the LLM step hallucinated anyway.
  • Wrong path: the agent took a sequence of steps it shouldn't have.
  • Forbidden action: the agent took an action it was never supposed to take.
  • Ignored failure: a tool errored and the agent reported success anyway, as in the example above.

Why it matters

If you only review final answers, you will rate failing runs as passing. The problem then repeats until a user complains.

Traces and spans

Watch: 2:12 to 3:47, then the walkthroughs at 10:48 and 14:23

In everyday life

Go back to the package tracking history. The whole history is one shipment's journey, and each line in it (picked up, arrived at depot, out for delivery) is a single scan with its own time, place and details.

Plain-English definition

A trace is the full record of one run of your agent, from the user's request to the final answer. A span is one operation inside that run, such as an LLM call, a retrieval, a tool call, a memory lookup or a hand-off. Each span holds its own inputs, outputs and execution details.

One user request goes in, many steps happen inside, and one answer comes out. Everything in between forms one trace. Instead of seeing only the input and output, you see the path the system took to get there.

Try it: read a real trace

This is the damaged-furniture refund from the video. Store policy says refunds over $500 must go to a human. Open each span to see its details.

    Read it like a reviewer

    • What did the user ask for?
    • Which span shows where the agent got the order total?
    • Which span shows it applied the $500 policy?
    • Did the tools it called match the policy?
    • Is every fact in the final reply backed by a span?

    The video also opens a simpler trace. A customer asks where order MP38291 is. The agent reasons that it needs to look up the order first, calls lookup_order, and replies that the order is in transit with FedEx, giving the tracking number. Every figure in the reply appears in the tool result, so you can tell the answer is grounded, meaning it was not made up.

    Often confused

    Trace vs. span

    A trace is the whole run. A span is one step in it. "One trace equals one run" is the rule of thumb from the video.

    Trace vs. error logs

    Error logs tell you when something crashed. A trace shows the whole path, including runs with no errors that still reached the wrong outcome.

    The traces-to-evals lifecycle

    Watch: 3:47 to 10:41

    In everyday life

    A good mechanic test-drives the car and listens for the noise. They find where it starts, name the fault, and add a check for it to the list the shop runs on every car that comes in.

    In AI agents

    Your agent's traces are the test drive. You read them, find where each run went wrong, name the failure types, then write checks (evals) that run automatically every time you change the agent.

    Open coding and axial coding

    Watch: 6:26 to 8:11

    In everyday life

    After a brainstorm, the wall is covered in sticky notes, each written however people felt like writing it. Then someone sorts them into groups and gives each group a name. The same notes become something you can act on.

    Plain-English definition

    Open coding means reading a sample of traces and writing short free-form notes on anything that went wrong. Axial coding means grouping those notes into named clusters. The set of clusters becomes your error taxonomy, a named list of the ways your agent fails.

    You don't need to read every trace. If the agent produced about a thousand traces in a day, sample 50 to 60 and review them one by one. In the video's example, 20 to 25 of those 50 had issues worth noting. The video's clusters were:

    • Context failure: the agent got the wrong information, or had the right information and didn't use it faithfully.
    • Decision failure: the LLM picked the wrong action or broke a policy.
    • Execution failure: a tool call errored, received bad arguments, or its failure was ignored.
    • Trajectory or cost issue: the path was too long, looped, or wasted time and tokens.

    The video names the four clusters. The one-line definitions above are working definitions for this module. The auto-generated captions call this step "actual coding," but the standard term from qualitative research is axial coding.

    5

    Choosing what to eval and how

    Watch: 8:11 to 10:02

    In everyday life

    A building inspector doesn't write a new code rule for every scuff on a wall. Rules exist for problems that keep happening and actually put people at risk.

    In AI agents

    Not every issue deserves an eval. Minor, one-off issues that don't really affect users can be noted and set aside. Promote a cluster into your eval taxonomy when it recurs, which the video puts at roughly ten or more traces, or when it hurts users.

    Step 1: write the rubric

    A rubric spells out how to recognize the issue: what counts as a pass, what counts as a fail, and when the check doesn't apply. Here is one for the refund policy from Section 2.

    Eval
    High-value refund escalation
    Pass
    Order total over $500 and escalate_to_human is called, with no process_refund call.
    Fail
    process_refund is called for an amount over $500.
    N/A
    No refund was requested in the trace.

    Step 2: pick the lightest evaluator that works

    Cheapest, fully repeatable

    Deterministic check

    Plain code with no model: conditions on status codes, errors, tool names, amounts, counts or latency.

    Example: the tool returned an error, or a refund over $500 has no escalation.

    Moderate

    Binary classifier

    A model that gives a yes/no label when a simple rule can't read the text reliably.

    Example: does this reply claim an action was completed?

    Most flexible, most costly

    LLM-as-a-judge

    A model that reasons against your rubric, for judgments that need understanding.

    Example: is every claim in the answer supported by the retrieved policy text?

    Often confused: evals vs. LLM-as-a-judge

    The misconception

    "Writing evals" means asking another LLM to grade the output.

    What the video says

    Evals can be deterministic checks, classifiers or LLM judges. Use an LLM judge only when the check needs reasoning.

    Try it: pick the evaluator

    For each check, choose the lightest evaluator that would do the job reliably.

    6

    Regression suites

    Watch: 9:54 to 10:41

    In everyday life

    After a plumber fixes the leak under your sink, you turn on the other taps and flush the toilet. You're making sure the fix didn't break something that worked yesterday.

    Plain-English definition

    A regression suite is the collection of evals built from the failures you've found. You rerun all of it after every change to the agent, whether that's a prompt edit, a new tool or a model swap. Old fixes should stay fixed and working behavior should keep working.

    Try it: ship a prompt change

    Your team shortened the system prompt to cut token costs. Every test passed yesterday. Run the suite before you ship.

    EvalCame fromTypeBefore changeAfter change
    The shorter prompt dropped the line about the $500 approval limit. The agent now refunds high-value orders on its own. Without the suite, this would have shipped, and customers would have found it first.

    Detections and AI-assisted investigation

    Watch: 18:20 to 24:34

    Deterministic detections: flag before you open

    Detections are simple rules with no LLM involved, applied to every trace as it comes in. Examples include a tool status other than 200, an error, high latency, a cost that is too high, or more than five tool calls, which suggests an inefficient path. They tell you which traces need attention before you open anything.

    Try it: turn detection rules on and off

    Watch which of today's traces get flagged for review.

    TraceRequestTool errorsTool callsLatencyCost

    Notice that the high-value refund processed without escalation in T-209 is never flagged by these rules. Detections catch mechanical problems. Policy and reasoning failures need the evals from Section 5, or a human reading the trace.

    AI investigators: faster, never final

    When there are too many traces or the spans are too long to read, you can ask an agent to do a first pass. In the video, the reviewer asks the platform's chat agent to investigate the support agent's traces thoroughly and list issue clusters with trace IDs. It came back with clusters including silent tool call failures, faked actions, fact hallucinations and cross-account order modifications.

    The investigator narrows down where to look. You still open every flagged trace and confirm it. As the video puts it, manual review is always required, whether the first pass was automated or not.

    Often confused

    False positive

    The investigator flagged an issue, but when you open the trace nothing is actually wrong.

    False negative

    A real issue exists in a trace, but the investigator didn't flag it. You'll only find these by sampling traces yourself.

    You opened each trace to check. Label each outcome.

    Lab: your first trace review

    Objectives

    • Produce an error taxonomy for one agent from a real sample of traces.
    • Write at least one rubric and choose its evaluator type.
    • Seed a regression suite you can rerun after every change.

    Steps

    Reflection questions

    • Which failure would you have missed if you had only read the final responses?
    • Which cluster was most common, and was it also the most harmful?
    • Which of your rubrics could be a deterministic check instead of an LLM judge?
    • What change are you planning to the agent next, and which evals would catch it breaking something?

    Final check

    Six questions across the whole module

    Choose an answer to see the explanation.

    Key takeaways

    • A confident final answer is not evidence of a successful run. Read the path.
    • One trace is one run, and each step inside it is a span with its own inputs and outputs.
    • Sample 50 to 60 traces, open-code them freely, then cluster the notes into a named error taxonomy.
    • Only recurring or harmful failures earn an eval, and each eval starts with a clear pass/fail rubric.
    • Evals aren't just LLM judges. Use deterministic checks wherever a rule is enough.
    • Collect the evals into a regression suite and rerun it on every change.
    • Detections and AI investigators speed up review, but a human still confirms every finding.
