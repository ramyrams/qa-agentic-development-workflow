Hands-on lab: trace, evaluate and fix a Copilot agent skill

The system under test is a real GitHub Copilot custom agent and its skill, running on Claude Sonnet 5. You'll run customer cases through it, read the traces it leaves behind, find failure patterns, turn them into evals, fix the skill, and prove the fix with a regression suite. It needs no API keys and no packages, only VS Code, Copilot and Node.js.

Time

About 100 minutes, or 15 minutes as a presenter demo.

Who it's for

Engineers who write Copilot agents, skills and prompt files, and the QA engineers who test them.

What you'll leave with

An error taxonomy, five evals, a fixed SKILL.md, and a regression suite that forces a re-run whenever the skill changes.

How the loop works

  1. RunThe Maple Support agent handles cases using its skill
  2. TraceThe skill's tool script records every call to runs/
  3. FindRead, open-code, cluster, detect, investigate
  4. EvalWrite rubrics and deterministic evals
  5. FixChange SKILL.md, re-run the cases, and npm test

Set up

10 min
  1. Check your tools: VS Code with GitHub Copilot Chat signed in, and Node.js 20+ (node -v). Nothing to install.The only runtime is Node. The "AI" is Copilot itself.
  2. Unzip maple-skill-lab-starter.zip and open the folder in VS Code. Push it to an Azure DevOps repo if you want your changes tracked.You'll commit after the eval step and after the fix, so you can diff the skill.
  3. In Copilot Chat, pick Agent mode and Claude Sonnet 5.If Sonnet 5 isn't in the picker, your admin may need to enable its model policy. Another Claude model works, but your traces will differ from the reference run.
  4. Check the customizations loaded. The agents dropdown should list Maple Support, Trace Investigator, eval-writer and skill-fixer. Typing / should show run-cases, open-code and cluster-issues.These all live in .github/. The lab uses every Copilot customization type: instructions, a scoped instructions file, custom agents with handoffs, prompt files and skills.

Two sides of the repo

SideFilesRole
System under test.github/agents/maple-support.agent.md, .github/skills/maple-support/, cases/, data/Handles customer cases. Its tool script writes the traces.
Evaluationevals/, scripts/, tests/, review/, and the investigator, eval-writer and skill-fixer agentsReads traces, finds failures, writes evals, fixes the skill.

The Maple Support agent is told never to open the evaluation side. If the agent under test can see the tests, you end up measuring whether it can pass the tests, not whether it follows policy.

1

Meet the skill under test

5 min
  1. Open .github/skills/maple-support/SKILL.md and data/policies/ side by side.The policies define correct behavior. The skill is the thing being tested, and it might be wrong.
  2. Open .github/skills/maple-support/scripts/maple.js and find the record() function.This is the instrumentation. Every tool call the agent makes is written as a span with input, output, status and timing. The trace also stores a hash of SKILL.md, so you always know which skill version produced it.
  3. Predict: write down any instruction in the skill that you think will cause a policy violation.You'll compare your prediction with what the traces show. Most people find two or three of the five problems by reading alone.

Which spans can you trust?

Tool spans

Recorded by the script from what actually happened. The model can't fake them.

Note and reply spans

Written by the model itself. A note says what the model claims it decided. Check it against the tool spans.

2

Run the cases and collect traces

10 min
  1. In Copilot Chat run: 
    /run-cases cases=all
    The prompt file switches to the Maple Support agent, which handles each of the 12 cases in cases/ with the skill. Approve each terminal command, or allow it for the session if your organization permits.
  2. When it finishes, run: 
    npm run list
npm test
    list shows every case's input and reply. npm test runs the regression suite on the 7 starter golden cases with the single starter eval.
  3. Commit the traces: git add runs && git commit -m "v1 traces".These are your baseline "production" traces.

Expected

Twelve files in runs/, and npm test green. As in the module, the suite passes because it can only catch what its one eval checks.

No Copilot access, or the run stalls?

Copy the recorded reference run into place with cp samples/reference-v1-runs/*.json runs/ and continue. It was produced by following SKILL.md v1 literally, so it shows every seeded flaw.

Batch or one chat per case?

Running all 12 cases in one chat is quick, but earlier cases stay in the model's context and can influence later ones. Production runs are independent. If a case behaves oddly, re-run it alone with /run-cases cases=C-07 in a new chat. Running start again replaces that case's trace.

3

Read traces by hand

10 min
  1. Read a correct run first: 
    npm run view -- C-06
    Find the span showing the $649 total, the note explaining the decision, and the create_ticket and escalate calls.
  2. Now compare two more: 
    npm run view -- C-07
npm run view -- C-09
    Read the reply first, then the spans. Ask whether the reply would pass if it were all you saw.
  3. Check a note against the tool spans. Does the model's stated reason match what the tools returned?

Checkpoint

The reply is often fine while the path is wrong. The model will usually explain its bad decision very clearly in a note, because the skill told it to act that way. That's why you judge against the policy, not against the skill.

4

Open coding

10 min
  1. Run: 
    /open-code
    Copilot reads every trace and appends free-form notes to review/open-coding.md, one row per problem with the evidence span.
  2. Verify each note yourself with npm run view -- <case>. Fix, delete or add notes.With 12 cases you can check every one. With a real agent you'd sample 50 to 60.
5

Axial coding: cluster and trace back to the skill

10 min
  1. Run: 
    /cluster-issues
    This fills in review/taxonomy.md with clusters, categories, counts and a column this lab adds: the SKILL.md instruction that most likely causes each cluster.
  2. Challenge each "likely cause." Is it a wrong instruction, a missing instruction, or the model ignoring a correct one?These need different fixes. A wrong instruction gets removed, a missing one gets added, and an ignored one may need to be clearer or checked by the tool script.
  3. Mark which clusters get an eval. With one case each, severity decides, not frequency.
6

Detections and the Trace Investigator

10 min
  1. Run npm run detect, then ask Copilot (Agent mode) to extend it: 
    Add detection rules to evals/detections.js: more than 5 tool calls, and a case with no reply.
Run npm run detect and tell me which clusters in review/taxonomy.md are still not flagged.
  2. Select Trace Investigator and send: 
    Investigate every trace in runs/. List failure clusters with case IDs, the proving span,
and the SKILL.md instruction behind each.
  3. Compare its output with your taxonomy and list confirmed findings, false positives and false negatives.

Expected (reference run)

Detections flag only 2 of the 5 failing cases: the tool error and the lookup loop. The invented date, the gold-tier refund and the order changed on another customer's account show up only through reading traces or through evals.

7

Rubrics and evals

15 min
  1. Read evals/trace-complete.eval.js, .github/skills/eval-authoring/SKILL.md and .github/instructions/evals.instructions.md.The scoped instructions apply automatically to any file under evals/. One rule matters most: evals take business rules from policy, never from SKILL.md.
  2. Click the investigator's Write evals for these clusters handoff, or select eval-writer, and send one cluster at a time: 
    Cluster: <paste the row from review/taxonomy.md>
Write the rubric first and stop so I can review it.
  3. Review the rubric, reply "write the eval", then check the output of npm run evals -- --verbose. The eval should fail on the cluster's case and pass everywhere else.
  4. Make sure each failing case is in data/golden.json, then run npm test and commit.

Expected (reference run)

Five evals, each failing on exactly one case: C-02, C-03, C-07, C-09 and C-10. npm test is now red, which is correct. The "claims success" eval is a pattern match standing in for a classifier. Discuss where it could give false positives.

8

Fix the skill and prove it

15 min
  1. Click the eval-writer's Fix the skill handoff, or select skill-fixer: 
    npm test is failing. Fix SKILL.md so the Maple Support agent follows data/policies/.
Remove conflicting instructions rather than adding exceptions. Show me the diff.
    The skill-fixer can edit only SKILL.md. It can't weaken an eval to make the suite pass.
  2. Review the diff, then run npm test before re-running anything.Every golden case now fails as stale, because its trace came from the old skill hash. A skill change isn't proven until the cases run again.
  3. Click Re-run the affected cases, or use /run-cases cases=all in a new chat.
  4. Run npm run evals and npm test, then commit the skill and the traces together.

Expected (reference run)

The stale check fails all 12 golden cases. After the re-run, every eval passes on all 12 cases and npm test passes 12 of 12.

9

Catch a regression

10 min
  1. A teammate "tidies" the skill. In the Damaged items section, replace the escalation sentences with "Look up the order and the customer, then refund the order total."
  2. Re-run the damaged-item cases in a new chat: /run-cases cases=C-05 C-06 C-07. Then re-run the rest, because npm test will flag them as stale.
  3. Run npm test, read the failure, restore the sentences, re-run, and confirm green.

Expected (reference run)

C-06 and C-07 fail refund-escalation with refunds of $649 and $1180. The eval still catches this because it reads the $500 limit from data/policies/returns.md, not from the skill that was just edited.

Why your run may differ

Claude Sonnet 5 in Copilot won't behave identically to a literal execution. It may ignore a flawed instruction on one run and follow it on the next. When a flaw doesn't show up, the skill is still wrong: the eval protects you on the day a model does follow it. Run the cases twice and compare the traces. Consistency between runs is part of what you're evaluating.

Wrap-up

Reflection questions

  • Which of the five flaws did you predict in Step 1, and which did only the traces reveal?
  • Which failures came from a wrong instruction, which from a missing one, and did the model ever ignore a correct one?
  • Where would the "claims success" check need a real classifier or an LLM judge?
  • Which of your team's skills changes most often, and what would its golden cases be?

Apply the pattern to your own skills

  1. Instrument the skill. Route its actions through a bundled script that records spans, and store a hash of SKILL.md in each trace.This gives you real traces of Copilot agent runs with no external platform.
  2. Keep test cases and policy outside the skill, in files the agent under test can't rewrite.The skill is the variable. The policy is the fixed definition of correct.
  3. Gate skill changes on npm test in your Azure DevOps pull request pipeline, with the stale-trace check on.Nobody can change SKILL.md without re-running the golden cases.
